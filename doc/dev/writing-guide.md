# 文档写作规范

写之前先确定一件事：这篇东西是**教程**、**任务指南**、**参考**，还是**原理说明**。四者混在一页里，读者就不知道自己是该跟着敲，还是该查表。

## 1. 四种体裁，四个位置

| 体裁 | 回答的问题 | 放哪 | 成功的标准 |
|---|---|---|---|
| 教程 tutorial | 我跟着做，能做出什么？ | `doc/user/tutorials/` | 读者照着敲完，产物一定跑得起来 |
| 任务指南 guide | 我要完成某件事，怎么做？ | `doc/user/guides/` | 读者按步骤解决了手上那个具体问题 |
| 参考 reference | 这个参数是什么、默认值多少、什么时候报错？ | `doc/user/api/`、`doc/user/config/` | 查得到，且与实际代码一致 |
| 原理 explanation | 为什么这样设计？为什么不能那样做？ | `doc/dev/`、`doc/guidebook.md` | 读者理解了取舍，不再重复踩坑 |

判断方法：如果一段文字里既有「跟着做」的步骤，又有参数表，还有设计动机，那它至少是两篇文档被塞进了一页。拆开，用链接连起来。

## 2. 教程：保证读者成功

教程的主角是读者手上的产物，不是 API。开头第一句就说清「做完会得到什么」，然后从第一个可见结果开始。

```
✗ 本教程将带领你逐步学习使用 sapdon 框架创建各种类型的物品。
✓ 跟着做完，创造菜单里会多一个「铁锭」，拿在手里能看到图标、放进工作台能合成。
```

几条硬要求：

- 每一步都写**怎么确认这一步成了**。命令的预期输出、文件路径、游戏里的现象，三选一。
- 只给一条路径。教程里出现「你也可以用 A，或者用 B」，读者就要停下来做选择，教程就断了。分支留给 guide。
- 示例代码必须能直接跑。避免 `...` 和「此处省略」，除非那是读者自己的业务代码。
- 不复述参考文档。参数含义写一句就够，要细节就链到 `api/`。

## 3. 任务指南：一个标题一个任务

标题写成读者会搜的话，不要写成目录项。

```
✗ 纹理教程
✓ 物品图标显示成紫黑格怎么查

✗ 构建与发布
✓ 把模组打成 .mcaddon 发给别人
```

正文结构固定为：**现象或目标 → 步骤 → 怎么确认成了 → 没成的话查什么**。不需要背景介绍，也不需要「本文将从三个方面展开」。

步骤里允许分叉，但要写清判据：

> 如果 `dev/` 里有 `.mcaddon`，直接发给玩家。没有的话，先回到第 2 步确认当前目录是不是项目根。

## 4. 参考：只描述，不劝说

参考文档里不写「推荐」「最佳实践」「强烈建议使用」。要推荐就写清条件和代价：「项目里同时装了别的 addon 时，两个包的 UUID 不能相同，否则引擎按同一个包处理」。

每个条目至少包含：签名或字段名、类型、默认值、什么情况下会失败。失败时的报错原文优先照抄，别改写成「可能会报错」。

## 5. 语言：像人在讲，别像模板在填

下面这些是从现有文档里挑出来的真实问题，改的时候对照着删。

**套话开场。** 「本教程将带领你逐步学习」「在现代模组开发中」直接删。第一句就给事实。

**破折号当万能连接符。** 「它不是 A —— 而是 B」「构建成功 —— 但产物是旧的」。一句话里塞两个转折，读者要读两遍。拆成两句，或者用逗号、冒号、括号。

**加粗当重音。** 一段里三处加粗，等于没有重点。加粗只留给「看错就会坏」的地方：路径大小写、六面顺序、必须删的文件名。

**列表吞掉因果。** 能用一段话说清的因果，不要拆成五个 bullet。列表适合并列项（六个面、三个构建模式），不适合论证。

**表格当收纳箱。** 表格适合字段对照和症状速查。把一段有前后依赖的操作步骤塞进表格，读者会横向读串行。

**三连排比和「不仅…而且…更…」。** 技术文档不需要修辞，需要信息增量。

**emoji 当警示牌。** `⚠️` 满篇都是的时候，真正的危险反而看不见。危险写进句子：「删掉 `dev/<name>_BP/manifest.json` 再构建，否则新的依赖不会写进去。」确实需要单独标出来的，用 `> **注意**：` 引用块。

**统一模板收尾。** 每篇结尾都是「## 下一步 + 三条链接 + 破折号说明」，这是模板的痕迹，不是作者的选择。相关链接只在真的相关时给，一到三条，用一句话串起来即可。

## 6. 事实必须能落地

写命令、路径、报错、行为之前，先在仓库里找依据：

- 命令与参数：`src/cli/` 下的实现，别照抄旧文档。
- 生成的字段：打开 `dev/` 里的真实产物，或者读 `src/core/`。
- 报错原文：`doc/dev/known-pitfalls.md` 或 ContentLog 里的原始行，逐字引用。
- 版本号：`package.json`、`src/templates/*/build.config`。

查不到就先别写，或者写成「未验证」。读者按文档操作失败一次，这份文档就作废了。

## 7. 提交前自查

- 这一页的体裁是什么？有没有混进另外两种？
- 开头第一句是不是「读者能得到什么」，而不是「本文将介绍」？
- 每个命令后面，读者知道怎么判断成功吗？
- 有没有为了凑结构而加的 `---`、加粗、表格、emoji？
- 有没有「综上」「值得注意的是」「不仅仅是」这类可删的词？
- 示例代码和路径，在仓库里找得到出处吗？
- 相关链接指向的文件真实存在吗？（改完路径跑一遍链接检查）
